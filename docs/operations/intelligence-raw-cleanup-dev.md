# DEV intelligence raw expiry: exact-plan execution

Status: proposed DEV-only implementation; **not deployed or provisioned**. Applies to EID Expedited only. V142 supplies immutable capture leases and append-only audit documents. V143 adds the separate approval table and checkpoint purge authority; it never creates an approval or deletes bytes. The complete pending migration set must be reviewed before any future dispatch.

## Authority and scope

- `OH_LYME_DEV_INTELLIGENCE_RAW_CLEANUP` is the executor role. The role, database/schema/warehouse usage, service user and credentials require the separately reviewed DEV security bootstrap before V143; the migration service cannot create account roles. It may read lease/copy metadata and approvals, insert redacted cleanup receipts, update the existing serialization guard, and call one purge procedure. It receives **no direct DELETE**.
- `OH_LYME_DEV_INTELLIGENCE_RAW_PURGE_OWNER` is unassigned. The security bootstrap grants its exact `SELECT, DELETE` dependency on `GOVERNANCE.INGESTION_RUN_PAYLOADS`; V143 grants approval/lease/guard reads and transfers ownership of only the checkpoint purge procedure. It is not granted to runtime or executor.
- The migration deployer owns the approval table and alone can insert a reviewed plan. The normal ingestion runtime has no privilege on approvals or the purge procedure. Approval rows record the plan hash, exact canonical private JSON, authenticated service user, independent approval reference, and time. Execution receipts are independently committed in V142's audit table before and after each physical mutation.
- The exact private plan enumerates DEV EID copies and an inventory hash. Only captures whose immutable `expires_at = captured_at + 30 days` has passed are eligible. Shared objects with a live claim are excluded. Execution recomputes the original inventory under the same serialization guard and rejects added or changed targets. A fresh successful HTTP 200 may create a new lease; a 304, replay, checkpoint, or cache action cannot renew one.

## Actual DEV persistence surfaces

`compose_pilot` uses Snowflake checkpoints and Spaces raw objects. Raw XML may be in `GOVERNANCE.INGESTION_RUN_PAYLOADS`, a content-addressed Spaces object, and process/conditional-cache buffers. Artifact-member reads point to the claimed Spaces object. Normalized records, revision/capture/provenance tables, and source registry rows remain untouched. Local file checkpoints and binary replay files are offline alternatives, not used by this DEV composition; the DEV executor rejects them. `INTELLIGENCE_RAW_RETENTION_DOCUMENTS` is lease/copy metadata and is retained as evidence, not deleted as raw transport.

## Bounded three-stage operation after provisioning and deployment

The operator runs `scripts/intelligence_raw_cleanup_dev.py` in an isolated, protected DEV job with a five-minute process deadline and 10-second statement timeout. It prints only plan hashes and outcome counts; the plan file contains private locators and must stay in a restricted, ephemeral workspace, never in Git, Actions logs, or public artifacts. Snowflake service identity is verified before the first inventory query. Spaces endpoint, bucket, prefix, and region are fixed to DEV; execution requires a separately scoped delete credential.

1. `plan --plan-file <private-new-file>`: under the cleanup service, inventory only EID raw claims and write an exact canonical plan with exclusive file creation. Review the private target list and captured-at/expiry evidence. An empty plan is a no-op.
2. `approve --plan-file <reviewed-private-file> --plan-sha256 <exact-hash> --approval-ref <review-record-id> --confirm`: under the separate migration/approval service, verify current inventory and exact hash, then record a single attributable approval. The review record must be independently approved; this command cannot supply that human decision. A changed plan fails.
3. `execute --plan-file <same-reviewed-private-file> --plan-sha256 <exact-hash> --confirm`: under the cleanup service and a DEV-prefix-scoped Spaces key, check that exact approval, revalidate inventory, append durable pending intents, delete only enumerated raw copies, then append outcomes. Return nonzero on failed copies. A retry of the same plan is idempotent; an unresolved pending receipt remains available after crash or commit uncertainty.

No routine runtime path invokes approval or cleanup. The exact plan requires human review, so an operational cadence and protected approval/execution environments must be provisioned and verified before claiming automatic physical deletion by day 30. Lease-based read expiry already occurs at the exact boundary even if physical cleanup is delayed. Do not register EID or acquire the feed until role/Spaces provisioning, V143 protected-path deployment, intended-role negative grants, synthetic DEV readback and an approved cleanup operating cadence are verified. NIH and PROD remain out of scope.
