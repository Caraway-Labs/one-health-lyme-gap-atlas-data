# Atlas semantic metadata v1

Status: Proposed for protected steward review. Owner: Atlas data stewardship and engineering. Executable validator: `src/lyme_gap_atlas_data/semantic_metadata.py`. Gap inventory: `story-191-metadata-gap-matrix-2026-09-24.md`. Identity authority: `atlas-semantic-domain-v1.md` and ADR 0035.

## Attachment, identity, and authority

One metadata document attaches to one #190 `(measure_id, semantic_version)` definition. Its `metadata_id` is deterministically `metadata:{measure_id}:{semantic_version}` and is never inferred from a label. The embedded #190 measure definition and its `meaning_signature` are required. `metadata_revision` starts at 1 and increases for reviewed metadata revisions; `revision_id` hashes the complete metadata content. Historical revisions remain immutable. Metadata is a definition attached to semantic identities, not a second measure registry or observation store. No V071/V072 or V100–V102 storage change is made.

The `definition`, `unit`, `denominator`, `allowed_value_states`, geography grain, temporal semantics, allowed strata, origin, and methodology version must match the embedded #190 measure. The definition cannot be authored by a non-authoritative generated summary. Field authority is explicit for label, definition, and short description: `SOURCE_REPORTED`, `STEWARD_REVIEWED`, `GOVERNED_GENERATED`, or `NON_AUTHORITATIVE_GENERATED_SUMMARY`. A generated summary must cite a prior `REVIEWED` metadata revision and cannot alter the authoritative definition. `steward_review` records `PENDING` or `REVIEWED` plus an explicit review date. A pending definition is a candidate, not a publication authorization.

| Change | Required handling |
| --- | --- |
| Cosmetic display label correction | Increment metadata revision; same measure ID/version and meaning signature. |
| Short explanation improvement without changing scientific meaning | Increment metadata revision; retain authoritative definition and measure version. |
| Steward-reviewed interpretation or use-boundary change | Increment metadata revision with `REVIEWED` state and revised limitation; if scientific meaning changes, create a reviewed new #190 semantic version/ID. |
| Applicability, unit, denominator, temporal meaning, origin, or permitted strata change | New #190 measure version/ID and metadata identity; old revisions remain readable. |
| Scientific definition/meaning or breaking consumer change | New reviewed #190 semantic version/ID; breaking consumer migration and API review remain separate. |
| Calculation implementation change with stable meaning | New referenced transformation/result revision, preserving exact prior lineage. |

`validate_metadata_revisions` rejects duplicate/gapped revisions and an unversioned meaning or definition change. Cross-version equivalence, deprecation, and generated compatibility matrices belong to #195. A new version does not itself grant comparability or source approval.

## Required fields and states

`contract_version`, `metadata_id`, `metadata_revision`, `revision_id`, `meaning_signature`, full `measure`, `label`, `definition`, `authority`, `steward_review`, `applicability`, `unit`, `denominator`, `allowed_value_states`, `provenance`, `freshness`, `quality_evidence`, `limitations`, and `visibility` are required. `short_description` is a required state envelope but its value may be `UNKNOWN`, `NOT_APPLICABLE`, or `UNAVAILABLE`. `summary_source_revision` is conditional on a non-authoritative generated summary; otherwise it is absent or null.

Every state envelope has exactly `state` and `value`: `KNOWN` requires nonempty text; `UNKNOWN` means the applicable fact is not established; `NOT_APPLICABLE` means the fact does not pertain to the measure; `UNAVAILABLE` means the fact cannot currently be obtained. All non-`KNOWN` values are JSON null. Empty strings never encode absence. The state envelope is used for optional descriptions, provenance fields, freshness dates, quality references, uncertainty, and evidence basis. It does not replace the separate #190 observation value-state vocabulary.

`applicability` repeats #190 geography grain, temporal semantics, permitted canonical strata, and reported/derived origin, so a mismatch fails. County-native measures use `COUNTY_NATIVE_STATUS`; site/event measures must state `NOT_COUNTY_REPRESENTATIVE`; source-only county evidence stays `UNKNOWN` with no inferred FIPS. This metadata does not define source-to-measure mappings (#192).

`provenance` carries safe publisher/source, governed dataset/product, exact source version and vintage, methodology version, and conditional transformation version. Source ID, dataset ID, source version, vintage, publisher and method version must be known; a derived measure also requires a known transformation version. The #158 shape accepts `infected-tick-calculation-v1`; the #159 coverage shape accepts `surveillance-coverage-calculation-v2`. A supplied allowlist of `(source_id, dataset_id, source_version_id)` from the governed source authority can reject stale or unapproved references. The validator cannot independently prove approval from a metadata fixture. Full run/artifact/record lineage and joins belong to #193; metadata does not copy those private values.

`freshness` keeps five separate facts: observation period/date, source vintage, retrieval timestamp, publisher publication/update date, and semantic metadata revision date. The first four can be explicitly unknown, not applicable, or unavailable; revision date is required and ISO formatted. A known period uses `YYYY-MM-DD/YYYY-MM-DD` in order; a known point/cumulative time uses an ISO date; a known retrieval uses a UTC ISO timestamp ending in `Z`. Publisher publication/update date and metadata revision date are dates, never inferred from retrieval or observation time. The vintage must equal the provenance vintage. No universal staleness threshold is invented; #157 `FRESHNESS_REVISION_STATE` remains authoritative for source-specific flags.

`quality_evidence` references #157 `surveillance-quality-profile-v1`, #166 `surveillance-quality-propagation-v1`, #159 `surveillance-scientific-eligibility-v1`, and #158/#159 result contracts where applicable. A derived measure must state an evidence basis allowed by its owning method: #158 permits `SYNTHETIC_FIXTURE` or `CURRENT_CODE_CI_TESTED_SOURCE_REPLAY_LIMITED`; #159 coverage permits `SYNTHETIC_FIXTURE` or `CURRENT_CODE_SOURCE_BACKED_REPLAY`. Neither value is inferred from metadata. `uncertainty` is an explicit state, not a confidence score. The metadata validator checks known contract IDs and required presence; it does not create weights, compute quality, approve scientific eligibility, or infer source-backed evidence. The referenced owning contracts retain their own validation and result revision rules.

Each limitation is `{category, code, text}`. Categories are `USE_RESTRICTION`, `INTERPRETATION`, `REPRESENTATIVENESS`, `DENOMINATOR`, `SOURCE`, and `METHOD`. Every measure requires an interpretation limitation; non-county shapes additionally require representativeness limits; measures with denominators require denominator limits. These machine-readable codes coexist with the owning #157–#159 reason codes and do not replace them. County tick `NO_RECORDS` never means absence; site/event records never prove county coverage; derived results never imply human risk.

`visibility` is `INTERNAL`, `CONSUMER_SAFE`, or `PUBLIC` as a metadata classification only. The latter two undergo recursive restricted-material checks using the repository's safe-path pattern. Internal #158/#159 derived definitions remain `INTERNAL`; this field never grants an API/public view. #194 owns any consumer projection and API coordination. Safe examples show publisher, source label, definition, unit, limitations, and methodology references without raw payload, private artifact, signed URL, credential, or restricted source identifier.

## Representative contract fixtures and compatibility

`examples/story-191-safe-metadata-fixtures.json` contains nine explicitly synthetic metadata fixtures, generated and validated by `tests/test_semantic_metadata.py`: human county surveillance, SVI county context, RUCC county category, county tick status, county pathogen status, NEON site/event collection, NEON pathogen testing, #158 infected-tick prevalence, and #159 surveillance coverage. They use #190 IDs, grains, time semantics, units, denominators, and states. `PENDING` review and fixture source versions are contract examples only; they do not establish a real approved source tuple, DEV/PROD replay, or permission to publish. The #158/#159 fixtures remain internal.

The existing county release still uses its five source slots, 3,144 counties, 14 observations per county, current pointer, score defaults, and V072 views. This contract is storage-neutral and does not add a Snowflake table, change source permissions, rewrite migrations, or generate a new public interface. No database integration or live consumer claim is made. #192 owns comprehensive mappings, #193 lineage implementation, #194 consumer output, and #195 cross-release compatibility gates.
