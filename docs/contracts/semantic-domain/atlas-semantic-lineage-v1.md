# Atlas semantic lineage v1

Status: Proposed for protected review. Owner: Atlas data stewardship and engineering. Executable validator: `src/lyme_gap_atlas_data/semantic_lineage.py`. Baseline inventory: `story-193-lineage-gap-matrix-2026-09-24.md`. Identity authority: `atlas-semantic-domain-v1.md` and ADR 0035. Metadata authority: `atlas-semantic-metadata-v1.md`.

## Purpose and scope

Lineage explains where an assertion came from and which governed records, proofs, method and revision produced it. An edge is evidence of ancestry, not source authorization, scientific comparability, county representativeness, or permission to publish. This storage-neutral relationship envelope joins existing governance ledgers, canonical records, immutable V071/V072 release lineage, and V100–V102 derived-result references. It creates no parallel lineage table and does not alter the county builder, current release pointer, or API views. The caller must obtain an authority snapshot under its existing least-privilege role; this contract does not grant access or perform a Snowflake query.

Each envelope pins `contract_version`, #190 `observation` plus its semantic key and immutable revision, complete #191 `metadata` plus its exact revision, one or more `edges`, a transformation ID/version and methodology version, optional exact derived result ID/revision, optional exact release ID/bundle/observation membership, `visibility`, and a deterministic `lineage_id`. The embedded #190/#191 validators run before relationship validation. A live adapter must supply the actual authority rows; passing a synthetic registry proves only contract behavior.

## Authority joins and cardinality

Each edge identifies publisher/source, governed dataset/product and resource key, exact source version/vintage, ingestion run, retained artifact ID and SHA-256, a safe source record ID or row hash, canonical record ID when one exists, and record revision. The validator resolves these against supplied `source_versions`, `runs`, `artifacts`, and `records` authority maps. It rejects orphan identities, version/run/artifact/hash disagreement, record disagreement, and duplicate record edges. `normalization_ref` and `eligibility_ref` are optional exact references to existing proof contracts, but if supplied must resolve to the same record and source version with an explicit contract version. This does not validate the scientific contents of those owning contracts or invent a new approval.

Reported assertions have exactly one source edge matching #190 provenance. Derived assertions require nonempty unique `input_ids`, a one-to-one input-to-record relation in the authority snapshot, matching #190 source anchors, a versioned transformation, an allowed evidence basis for the owning #158/#159 method, and an immutable result revision matching method, evidence basis, semantic revision, and exact input set. This supports one-to-one, one-to-many, and many-to-one transformations without assuming one source record per output. Input and edge order do not change the lineage or #190 revision identity; repeated references to the same record fail closed. The #191 metadata source tuple is a safe representative source anchor, while the edge list is the complete multi-source lineage.

The `release` relationship is optional. When present, its ID, bundle hash, semantic revision membership and physical release observation ID must agree with one exact authority release. A cross-release guess fails. Source-only geography cannot claim release inclusion or a canonical county record. It retains the source geography, unresolved reason and any mapping attempt/proof; #190 requires null county FIPS and `UNKNOWN`. Native NEON site/event observations retain `NOT_COUNTY_REPRESENTATIVE`, even when a contextual county relationship has separate proof.

## Immutability and evidence

Source revisions and superseded records retain their original version/run/artifact/record IDs. Repeated acquisition has a distinct run and artifact and therefore a distinct lineage identity; identical replay against the same pinned inputs yields the same identity. A changed source revision, source edge, normalization/eligibility proof, method version, evidence basis, result revision, metadata revision or release membership changes lineage identity. Changed #190 scientific input sets change the observation key; changed payload at the same scientific scope changes its immutable revision. A new lineage envelope never rewrites a prior one or silently points it at a newer source. A batch rejects duplicate immutable lineage IDs. Historical V071/V072 and V100–V102 rows remain as stored.

Evidence basis is taken from the owning #158/#159 contracts. `SYNTHETIC_FIXTURE` remains distinct from `CURRENT_CODE_CI_TESTED_SOURCE_REPLAY_LIMITED` and `CURRENT_CODE_SOURCE_BACKED_REPLAY`. A lineage edge or metadata revision cannot upgrade one class to another. The tests in this story are synthetic fixtures and do not establish source-backed replay, live Snowflake lineage, source approval, or public consumer behavior.

## INTERNAL and CONSUMER_SAFE

`INTERNAL` may carry governance IDs needed for exact joins under existing role controls. `consumer_safe_lineage()` emits an explicit allowlist: semantic/metadata IDs and revisions, measure/version, publisher, dataset, source version/vintage, method/version, typed limitations, evidence basis, representativeness, safe record references, and optional result/release IDs. It excludes artifact IDs, hashes, runs, raw payloads, private paths and signed URLs. The safe-value guard rejects restricted keys and values, credentials, private keys, private workbook paths, and sensitive operational identifiers in emitted fields. This projection is a contract function, not a new public API or exposure approval; #194 owns PUBLIC and service integration. #158/#159 derived shapes remain internal until separately reviewed.

## Validation and evidence boundary

`validate_lineage()` verifies an envelope against explicitly supplied authoritative objects; `validate_lineages()` additionally rejects duplicate immutable IDs. The Story #193 fixture suite exercises ten representative traces and adversarial orphan, mismatch, hash, duplicate, method, evidence, release and safe-value cases. #192 owns comprehensive live source-to-semantic mappings; #195 owns the generated compatibility/version regression framework. No database behavior changes here, so Snowflake integration and protected role checks are not represented as passing evidence. Current county release behavior and public views stay unchanged.
